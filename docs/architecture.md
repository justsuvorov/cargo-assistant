# Архитектура

Принцип: **код проверяет, LLM помогает**. В прошлом MVP около 80% ошибок пришлось на поля,
которые проверяются обычным кодом (даты, суммы, «заполнено»). Поэтому LLM получает только
смысловые вопросы (груз, территория маршрута), извлечение профиля полиса и компиляцию базы знаний.

## Стек

| Слой | Выбор |
|---|---|
| Язык | Python 3.12 |
| HTTP | FastAPI |
| Интерфейс | Jinja2 + HTMX + немного чистого JS (drag-and-drop) |
| Домен | `typing.Protocol` + неизменяемые `@final`-классы |
| Границы (LLM, API, настройки) | pydantic v2 (`frozen=True`), в домен не проникает |
| БД | SQLAlchemy 2 (async) + Alembic; Postgres в проде, SQLite локально |
| Очередь | таблица `jobs` + отдельный процесс-воркер |
| Файлы | локальное хранилище на общем томе (RWX PVC в k8s) |
| Вход | Keycloak (OIDC), роли и группы; режим разработки без Keycloak |
| LLM | шлюз ВСК, OpenAI-совместимый `/v1/chat/completions`, через `httpx` |
| Чтение файлов | `openpyxl` (.xlsx), `xlrd` (.xls), `python-docx` (.docx), .doc — через LibreOffice headless |
| Поставка | Docker; docker-compose (api, worker, postgres); k8s (api, worker, PVC, ingress, secrets) |

## Пакеты и зависимости

Структура — в [CLAUDE.md](../CLAUDE.md). Направление зависимостей:

```
web, jobs ──► rules, declarations, policy, semantic, reports, storage, auth, core ──► domain
semantic, policy, knowledge ──► llm ──► domain
rules ──► domain (Semantics — интерфейс; реализация из semantic подставляется в jobs)
```

- `domain` ни от чего не зависит.
- `declarations`, `rules`, `reports` — чистый код без сети и БД.
- `jobs` и `web` только собирают конвейеры.

## Модель данных

```
Policy (номер ГП, страхователь, группа доступа)
 ├─ PolicyDocument   (вид: ГП | ДС N | особые условия | перечень перевозчиков; ключ файла;
 │                    номер ДС; дата вступления; к каким декларациям относится; изменяемые пункты)
 ├─ PolicyProfile    (версия, JSON по схеме, status: draft → approved, approved_by, approved_at)
 └─ Declaration      (ключ файла, номер, форма, число перевозок, месяц, ссылка на Job, result_key,
                      binding — итог привязки к полису: bound | policy_missing | policy_unreadable
                      | policy_unknown | policy_ambiguous)
      └─ CheckResult (строка «200» или «200/N» × поле: статус, код причины, ссылка на пункт,
                      комментарий, источник rule|llm, исправление эксперта)
RuleSet              (версия: исходник базы знаний → карточки, status: draft → active)
Job                  (тип: profile_build | reconcile | kb_compile; payload; status; stage;
                      progress 0–100; attempts; locked_at; error; created/updated)
EvalRun              (версия кода и карточек, точность по полям, время, число вызовов LLM)
LLMCall              (job, назначение, хэш промпта, токены, задержка, результат валидации)
```

Месяц декларации — по дате начала периода страхования первой перевозки (решение D-1).

## Конвейеры

```
Полис:       загрузка пакета (ГП, ДС, особые условия, перевозчики)
             → [profile_build] LLM извлекает профиль в JSON по схеме → эксперт ФСЦ проверяет → approved
База знаний: загрузка файла → [kb_compile] разделы → карточки полей → админ проверяет → active
Декларация:  drag-and-drop N файлов → N задач [reconcile]:
   ingest → форма и поля (без LLM) → нормализация → привязка к полису по «№ ГП»
   → для каждой карточки: редакции пунктов на дату начала перевозки → проверка кодом
   → смысловые карточки: одинаковые значения один раз, один пакет на карточку, параллельно
   → CheckResult в БД → «200 – результат проверки.xlsx» (особые условия — на отдельном листе, БТ-3b)
```

Привязка (T-26): номер ГП из поля «№ Генерального полиса» нормализуется по `params.ignore`
карточки `policy` и ищется среди полисов той же группы доступа. Найден ровно один — декларация
привязана (`bound`). Номера нет (`policy_missing`), он не прочитан (`policy_unreadable`), полиса
нет (`policy_unknown`) или их несколько (`policy_ambiguous`) — задача не падает и идёт дальше
без полиса: проверки по пунктам полиса дадут «требует проверки», причина видна на странице
задачи, в журнале — только код. Перепривязка при появлении полиса — только перезапуском задачи.

Если профиль полиса не подтверждён, задача `reconcile` ждёт со статусом «ожидает профиль
полиса». Активные карточки и профиль воркер читает из БД в каждой задаче, поэтому изменения
применяются без перезапуска (БТ-4).

Бюджет вызовов LLM на декларацию: не больше числа смысловых карточек формы (сейчас 3: груз,
отправление, назначение), независимо от числа строк.

## Результат

Отдельный файл на каждый файл декларации: «200 – результат проверки.xlsx». Колонки: Номер
декларации/строки | Наименование поля в декларации | С каким пунктом Ген. полиса сверено |
Результат проверки | Комментарий по сверке. Набор и порядок строк зависит от **формы**
декларации (вертикальная — 15 полей, ПСГ — 13 полей), нумерация — от **числа перевозок**
(«200» или «200/N»). Цвет статуса: совпадает — зелёный, не совпадает — красный, требует
проверки — жёлтый. Второй лист — особые условия по полису.

## Очередь и воркер

- Захват задачи атомарно: в Postgres `SELECT … FOR UPDATE SKIP LOCKED`, в SQLite —
  `UPDATE … WHERE status='queued'`.
- Одновременных задач в воркере — `WORKER_MAX_JOBS`.
- Зависшие задачи возвращаются в очередь по `locked_at`, но не больше `WORKER_MAX_ATTEMPTS` раз.
- Каждая задача обновляет `stage` и `progress`; страница опрашивает статус через HTMX раз в 1–2 с.
- Задачи идемпотентны: повторный запуск перезаписывает свой результат.
- Синхронный код выполняется в потоках; смысловые проверки внутри задачи идут параллельно.

## Клиент LLM

- Интерфейс `Model.answer(purpose, messages, schema) -> BaseModel`; код — `app/llm/`, подробности — [llm-gateway.md](llm-gateway.md).
- Провайдер выбирается `LLM_PROVIDER`: `vsk` (шлюз в контуре, по умолчанию), `anthropic`, `gemini`. Внешние
  провайдеры включаются только при `LLM_ALLOW_EXTERNAL=true` и только для обезличенных или вымышленных данных (П-17).
  У Anthropic `temperature` не передаётся (по данным агента T-04, текущие модели его не принимают), поэтому
  детерминизм гарантирован только у ВСК и Gemini.
- TLS проверяется всегда; корпоративный CA — `LLM_CA_BUNDLE`.
- `POST {LLM_API_URL}`, `Authorization: Bearer {LLM_API_KEY}`, поля `model`, `messages`,
  `max_tokens`, `temperature=0`, `thinking_token_budget`.
- Если шлюз поддерживает `response_format` / `guided_json` — ответ ограничивается схемой;
  иначе схема в промпте и проверка pydantic.
- Рассуждения `<think>…` вырезаются, включая незакрытый тег.
- Ретраи только на сетевые ошибки и 429/5xx с ограничением общего времени. Невалидный JSON —
  один повтор, затем исключение → «требует проверки».
- Общий семафор `LLM_MAX_CONCURRENCY` на процесс. Каждый вызов пишется в `LLMCall`.
- `FakeModel` с записанными ответами для тестов; сеть в тестах запрещена.
- Прошлый MVP падал целиком, когда шлюз отвечал 500 на чтении ДС (декл. 7, 29). Сбой
  извлечения одного документа полиса не должен ронять сверку: профиль остаётся черновиком
  с пометкой, какой документ не прочитан.

## Хранилище

```
policies/{policy_id}/documents/{имя файла}
declarations/{declaration_id}/source/{имя файла}
declarations/{declaration_id}/result/{номер} – результат проверки.xlsx
knowledge/{ruleset_id}/source/{имя файла}
```

Ключ проверяется на выход за корень хранилища. Права на файл — через группу полиса в БД.

Конвертация `.doc` (LibreOffice) работает в `SOFFICE_DIR` (по умолчанию `STORAGE_DIR/soffice`):
`cache/` — сконвертированные файлы по sha256, `profiles/` — профили LibreOffice, `work/` —
рабочие копии пакетов и деклараций. Системная временная папка не используется. Ежедневная
задача очистки удаляет файлы старше `SOFFICE_CACHE_DAYS` (7 дней) и свободные профили: в них
тексты документов клиента и история открытых файлов.

## Интерфейс и роли

Страницы: Полисы (загрузка пакета, просмотр и подтверждение профиля), Сверка (drag-and-drop,
очередь с прогрессом), Результат декларации (таблица, особые условия, скачивание, исправление
статуса экспертом), Архив (фильтр по месяцу и полису, архив), База знаний (карточки, подтверждение,
активация), Качество (прогоны эталона).

Роли Keycloak (названия уточнить): `cargo_user` — загрузка деклараций и просмотр; `cargo_expert` —
загрузка пакетов полисов, правка и подтверждение профилей, исправление результатов; `cargo_admin` — база знаний и качество.
Видимость данных — по группе.

## Конфигурация и наблюдаемость

Переменные окружения (`pydantic-settings`): `DATABASE_URL`, `STORAGE_DIR`, `LLM_API_URL`,
`LLM_API_KEY`, `LLM_MODEL`, `LLM_MAX_TOKENS`, `LLM_THINKING_BUDGET`, `LLM_MAX_CONCURRENCY`,
`LLM_TIMEOUT`, `LLM_TOTAL_TIMEOUT`, `LLM_PROVIDER`, `LLM_ALLOW_EXTERNAL`,
`LLM_RESPONSE_FORMAT`, `LLM_VERIFY_TLS`, `LLM_CA_BUNDLE`, `ANTHROPIC_*`, `GEMINI_*`, `WORKER_MAX_JOBS`, `WORKER_POLL_INTERVAL`, `WORKER_JOB_TIMEOUT`,
`WORKER_MAX_ATTEMPTS`, `SOFFICE_DIR`, `SOFFICE_CACHE_DAYS`, `KEYCLOAK_*`. Секреты — через k8s secret. Полный список с комментариями — `.env.example`.

Логи на русском, с `job_id` и `declaration_id`. Время каждой стадии логируется и сохраняется;
по этим данным проверяется НФТ-В.

## Мониторинг (D-34)

Журнал пишет приложение; дашборд и алерты в Superset читают только представления `v_*` в
схеме `monitoring`. Мы создаём таблицы и представления; дашборд, рассылку алертов на почту и
права на чтение настраивает пользователь. Представления создаются миграцией и существуют только
в Postgres; в SQLite их нет. Журнал хранится 3 месяца: строки старше удаляет ежедневная
задача очистки.

Термины (П-23): сессия — запуск проверки одной декларации (`reconcile`); статусы — «совпадает»,
«не совпадает», «требует проверки»; чанк — один вызов модели при проверке декларации; гонка
при загрузке — запуск нескольких задач по одной декларации, пока прежняя не завершена.

Таблицы журнала (новые или дополненные):

| Таблица | Что пишется |
|---|---|
| `worker_heartbeats` | воркер (хост, процесс, версия), время старта, последний сигнал раз в 30 с, сколько задач в работе |
| `job_runs` | каждая попытка задачи: воркер, начало, конец, исход (успех, ошибка, таймаут, возврат в очередь, ожидание профиля), класс ошибки, время стадий, версии кода, карточек, профиля, промптов и модели |
| `jobs` (+) | кто загрузил, группа доступа, sha256 файла, итоговый исход, время завершения |
| `llm_calls` (+) | исход вызова (успех, повтор, невалидный JSON, таймаут), карточка или документ, число вопросов в пакете, число отброшенных значений |
| `declarations` (+) | ожидаемых мест (перевозки × поля формы) и мест с ответом |
| `check_results` (+) | время записи |

Метрики для сверки деклараций:

| Метрики | Представление | Что считает у нас |
|---|---|---|
| основа графиков | `v_runs`, `v_session_outcomes` | попытки; итог сессии (проверки одной декларации) |
| 15 | `v_worker_status` | живость воркеров по `worker_heartbeats` |
| 16, 17 | `v_queue_status` | задачи в очереди и в работе сейчас, по типам |
| 18 | `v_queue_wait_daily` | ожидание от постановки до захвата: среднее, p50, p95 |
| 19 | `v_stuck_sessions` | задачи `processing` на воркере без сигнала |
| 22 | `v_outcomes_daily` | доли исходов сессий по дням |
| 23, 25 | `v_errors_daily` | ошибки по классам; гонка — несколько задач по одной декларации (тот же sha256 файла) одновременно |
| 24 | `v_failure_streak` | неуспешные попытки подряд |
| 28, 30 | `v_completeness_daily` | доля мест с ответом; чанки (вызовы модели) и упавшие из них |
| 29 | `v_unprocessed_reasons_daily`, `v_unprocessed_rows` | места без ответа и «требует проверки» по техническим причинам (`clause.unsettled`, `llm.*`, нечитаемый файл) |
| 31 | `v_rejections_daily` | отбракованные ответы модели: невалидный JSON, значение не найдено в тексте |
| 32 | `v_duration_daily` | длительность сессии и стадий: среднее, p50, p95, максимум |
| 55 | `v_status_distribution_daily` | «совпадает» / «не совпадает» / «требует проверки» по дням и полям |
| 65 | `v_versions` | те же метрики в разрезе версий кода, карточек, профиля, промптов и модели |
| 73, 74 | `v_usage_daily`, `v_usage_weekly` | пользователи, загрузки, декларации, перевозки |
| алерты | `v_alerts` | девять алертов, пороги — в самом представлении |

Алерты и стартовые пороги (пересмотр через две недели, T-24):

| Алерт | Срабатывает, когда |
|---|---|
| `worker_down` | нет сигнала работающего воркера больше 3 минут |
| `queue_stalled` | задача ждёт в очереди больше 15 минут |
| `stuck_sessions` | есть задача `processing` на неживом воркере |
| `consecutive_failures` | 3 неуспешные попытки подряд |
| `failure_share_1h` | больше 20% неуспешных сессий за час, если их не меньше 5 |
| `upload_race_1h` | есть гонка при загрузке за час |
| `low_completeness_1h` | есть сессия с заполнением ниже 95% за час |
| `failed_chunks_1h` | есть упавший вызов модели за час |
| `status_shift` | доля «совпадает» за сутки отличается от прошлых 30 дней больше чем на 20 п. п., если в каждом периоде не меньше 500 строк |

В журнал и представления не попадают значения полей, имена файлов и тексты документов: только
идентификаторы, коды, счётчики и время. Текст ошибки хранится в `job_runs`, но в представления
выводится только её класс.

Для Superset `v_alerts` даёт по строке на алерт: `alert`, `firing` (0 или 1), `value`,
`threshold`, `note`. Алерт в Superset — запрос `SELECT firing FROM monitoring.v_alerts WHERE
alert = '<имя>'` с условием «больше 0»; готовые запросы — в docs/monitoring.md.
