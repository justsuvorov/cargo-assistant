# Архитектура

Принцип: **код проверяет, LLM помогает**. В прошлом MVP около 80% ошибок пришлось на поля,
которые проверяются обычным кодом (даты, суммы, «заполнено»). Поэтому LLM получает только
смысловые вопросы (груз, территория маршрута), извлечение профиля полиса и компиляцию базы знаний.

## Стек

| Слой | Выбор |
|---|---|
| Язык | Python 3.12 |
| HTTP | FastAPI |
| Интерфейс | Jinja2 + HTMX + немного чистого JS (drag-and-drop) |
| Домен | `typing.Protocol` + неизменяемые `@final`-классы |
| Границы (LLM, API, настройки) | pydantic v2 (`frozen=True`), в домен не проникает |
| БД | SQLAlchemy 2 (async) + Alembic; Postgres в проде, SQLite локально |
| Очередь | таблица `jobs` + отдельный процесс-воркер |
| Файлы | локальное хранилище на общем томе (RWX PVC в k8s) |
| Вход | Keycloak (OIDC), роли и группы; режим разработки без Keycloak |
| LLM | шлюз ВСК, OpenAI-совместимый `/v1/chat/completions`, через `httpx` |
| Чтение файлов | `openpyxl` (.xlsx), `xlrd` (.xls), `python-docx` (.docx), .doc — через LibreOffice headless |
| Поставка | Docker; docker-compose (api, worker, postgres); k8s (api, worker, PVC, ingress, secrets) |

## Пакеты и зависимости

Структура — в [CLAUDE.md](../CLAUDE.md). Направление зависимостей:

```
web, jobs ──► rules, declarations, policy, semantic, reports, storage, auth, core ──► domain
semantic, policy, knowledge ──► llm ──► domain
rules ──► domain (Semantics — интерфейс; реализация из semantic подставляется в jobs)
```

- `domain` ни от чего не зависит.
- `declarations`, `rules`, `reports` — чистый код без сети и БД.
- `jobs` и `web` только собирают конвейеры.

## Модель данных

```
Policy (номер ГП, страхователь, группа доступа)
 ├─ PolicyDocument   (вид: ГП | ДС N | особые условия | перечень перевозчиков; ключ файла;
 │                    номер ДС; дата вступления; к каким декларациям относится; изменяемые пункты)
 ├─ PolicyProfile    (версия, JSON по схеме, status: draft → approved, approved_by, approved_at)
 └─ Declaration      (ключ файла, номер, форма, число перевозок, месяц, ссылка на Job, result_key)
      └─ CheckResult (строка «200» или «200/N» × поле: статус, код причины, ссылка на пункт,
                      комментарий, источник rule|llm, исправление эксперта)
RuleSet              (версия: исходник базы знаний → карточки, status: draft → active)
Job                  (тип: profile_build | reconcile | kb_compile; payload; status; stage;
                      progress 0–100; attempts; locked_at; error; created/updated)
EvalRun              (версия кода и карточек, точность по полям, время, число вызовов LLM)
LLMCall              (job, назначение, хэш промпта, токены, задержка, результат валидации)
```

Месяц декларации — по дате начала периода страхования первой перевозки (решение D-1).

## Конвейеры

```
Полис:       загрузка пакета (ГП, ДС, особые условия, перевозчики)
             → [profile_build] LLM извлекает профиль в JSON по схеме → эксперт ФСЦ проверяет → approved
База знаний: загрузка файла → [kb_compile] разделы → карточки полей → админ проверяет → active
Декларация:  drag-and-drop N файлов → N задач [reconcile]:
   ingest → форма и поля (без LLM) → нормализация → привязка к полису по «№ ГП»
   → для каждой карточки: редакции пунктов на дату начала перевозки → проверка кодом
   → смысловые карточки: одинаковые значения один раз, один пакет на карточку, параллельно
   → CheckResult в БД → «200 – результат проверки.xlsx» (особые условия — на отдельном листе, БТ-3b)
```

Если профиль полиса не подтверждён, задача `reconcile` ждёт со статусом «ожидает профиль
полиса». Активные карточки и профиль воркер читает из БД в каждой задаче, поэтому изменения
применяются без перезапуска (БТ-4).

Бюджет вызовов LLM на декларацию: не больше числа смысловых карточек формы (сейчас 3: груз,
отправление, назначение), независимо от числа строк.

## Результат

Отдельный файл на каждый файл декларации: «200 – результат проверки.xlsx». Колонки: Номер
декларации/строки | Наименование поля в декларации | С каким пунктом Ген. полиса сверено |
Результат проверки | Комментарий по сверке. Набор и порядок строк зависит от **формы**
декларации (вертикальная — 15 полей, ПСГ — 13 полей), нумерация — от **числа перевозок**
(«200» или «200/N»). Цвет статуса: совпадает — зелёный, не совпадает — красный, требует
проверки — жёлтый. Второй лист — особые условия по полису.

## Очередь и воркер

- Захват задачи атомарно: в Postgres `SELECT … FOR UPDATE SKIP LOCKED`, в SQLite —
  `UPDATE … WHERE status='queued'`.
- Одновременных задач в воркере — `WORKER_MAX_JOBS`.
- Зависшие задачи возвращаются в очередь по `locked_at`, но не больше `WORKER_MAX_ATTEMPTS` раз.
- Каждая задача обновляет `stage` и `progress`; страница опрашивает статус через HTMX раз в 1–2 с.
- Задачи идемпотентны: повторный запуск перезаписывает свой результат.
- Синхронный код выполняется в потоках; смысловые проверки внутри задачи идут параллельно.

## Клиент LLM

- Интерфейс `Model.answer(purpose, messages, schema) -> BaseModel`.
- `POST {LLM_API_URL}`, `Authorization: Bearer {LLM_API_KEY}`, поля `model`, `messages`,
  `max_tokens`, `temperature=0`, `thinking_token_budget`.
- Если шлюз поддерживает `response_format` / `guided_json` — ответ ограничивается схемой;
  иначе схема в промпте и проверка pydantic.
- Рассуждения `<think>…` вырезаются, включая незакрытый тег.
- Ретраи только на сетевые ошибки и 429/5xx с ограничением общего времени. Невалидный JSON —
  один повтор, затем исключение → «требует проверки».
- Общий семафор `LLM_MAX_CONCURRENCY` на процесс. Каждый вызов пишется в `LLMCall`.
- `FakeModel` с записанными ответами для тестов; сеть в тестах запрещена.
- Прошлый MVP падал целиком, когда шлюз отвечал 500 на чтении ДС (декл. 7, 29). Сбой
  извлечения одного документа полиса не должен ронять сверку: профиль остаётся черновиком
  с пометкой, какой документ не прочитан.

## Хранилище

```
policies/{policy_id}/documents/{имя файла}
declarations/{declaration_id}/source/{имя файла}
declarations/{declaration_id}/result/{номер} – результат проверки.xlsx
knowledge/{ruleset_id}/source/{имя файла}
```

Ключ проверяется на выход за корень хранилища. Права на файл — через группу полиса в БД.

## Интерфейс и роли

Страницы: Полисы (загрузка пакета, просмотр и подтверждение профиля), Сверка (drag-and-drop,
очередь с прогрессом), Результат декларации (таблица, особые условия, скачивание, исправление
статуса экспертом), Архив (фильтр по месяцу и полису, архив), База знаний (карточки, подтверждение,
активация), Качество (прогоны эталона).

Роли Keycloak (названия уточнить): `cargo_user` — загрузка и просмотр; `cargo_expert` —
подтверждение профилей и исправление результатов; `cargo_admin` — база знаний и качество.
Видимость данных — по группе.

## Конфигурация и наблюдаемость

Переменные окружения (`pydantic-settings`): `DATABASE_URL`, `STORAGE_DIR`, `LLM_API_URL`,
`LLM_API_KEY`, `LLM_MODEL`, `LLM_MAX_TOKENS`, `LLM_THINKING_BUDGET`, `LLM_MAX_CONCURRENCY`,
`LLM_TIMEOUT`, `WORKER_MAX_JOBS`, `WORKER_POLL_INTERVAL`, `WORKER_JOB_TIMEOUT`,
`WORKER_MAX_ATTEMPTS`, `KEYCLOAK_*`. Секреты — через k8s secret.

Логи на русском, с `job_id` и `declaration_id`. Время каждой стадии логируется и сохраняется;
по этим данным проверяется НФТ-В.
