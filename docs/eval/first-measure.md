# Первый замер: движок проверок в eval (T-10)

Конвейер `checked`: файл декларации читается `app.declarations`, каждая карточка `cards/`
проверяет своё поле через `app.rules`, полис — `Vacant` с номером ГП из шапки (профиля полиса
ещё нет), смысловые проверки — заглушка `tools.eval.semantics.Doubt` («требует проверки»,
код `eval.semantic`, каждая пачка вопросов — один вызов). Модель и сеть не используются.

Эталон v1, 232 строки, 11 деклараций; деление dev (8 деклараций, 158 строк) / holdout
(3 декларации). Спорных строк нет. Сравнение только с эталоном.

Полные отчёты (одна версия кода для всех шести прогонов):

| dev | [v1-dev-stub.md](runs/v1-dev-stub.md) | [v1-dev-match.md](runs/v1-dev-match.md) | [v1-dev-checked.md](runs/v1-dev-checked.md) |

Команда:

```
python -m tools.eval run --pipeline checked --part dev|all --real "<каталог unpacked>" --out …
```

- sum, «требует проверки» (70, 164): ответ верен случайно — причина `clause.absent`, а эталон

  005 этот риск есть: с профилем полиса проверка станет сверкой с перечнем перевозчиков, и
  результат может измениться.

Разбор: ни одно расхождение не вызвано разбором там, где проверка дошла до значения. Пустые
значения (`*.empty`, 6 мест в dev, 8 во всём) все совпали с ожиданием ФСЦ. Значения полей с
`clause.absent` движок не оценивал, поэтому качество их разбора этим замером не проверено.
Ответы вне эталона (47 / 53) — места, которых нет в ответе MVP (в основном 114, 35, 271);
пропущенных мест эталона нет.

Спорная разметка: в эталоне v1 спорных строк нет. Расхождения beneficiary и carrier — вопрос
к правилу карточки, на который разметка ФСЦ отвечает «совпадает» (вопросы ниже).

## Независимое ревью

1. Конвейер эталона не видит: `Checked` получает каталог деклараций и папку карточек, номер
   декларации — единственное, что приходит из эталона.
2. **Утечка через карточки.** В `evidence` и `clarify` карточек — замечания ФСЦ к тем же
   строкам, из которых собран эталон, в том числе к holdout (164, 263, 271). Все 4 найденных
   «не совпадает» в полях без полиса (beneficiary 97 и 70, transshipment 97 и 271/1) прямо
   названы в карточках. Точность этих полей — оценка на обучающей выборке, holdout для карточек
   не независим. Честная контрольная часть — только новые декларации, размеченные по шаблону.
3. **Эталон почти не различает проверку и «всё совпадает».** В 7 из 9 полей без полиса
   (carrier, document, document_date, document_number, other, packaging, sealing) эталон не
   ждёт ни одного «не совпадает»: заглушка match там набирает 100%. Нужны отрицательные
   примеры.
4. Цифры `checked` подозрительно хорошими не выглядят: общий уровень ниже match, расхождения
   объяснены построчно.

## Предложения (не исправлено: вне зоны eval)

1. Движок, `date_range`: проверка «окончание не раньше начала» (`end_before_start`) не требует
   полиса, но `Grounded` сначала запрашивает пункт `term` и при его отсутствии отвечает
   `clause.absent`. Если проверять порядок дат раньше пункта, 97 × period найдётся без профиля.
2. Движок, `Party`: ОПФ, слитая со следующим словом («…LLCAddress…»), не распознаётся.
   Нужно решение, что считать границей ОПФ, — или признать это особенностью данных.
3. Карточки beneficiary и carrier: иностранная ОПФ — «требует проверки» (вопрос в `clarify`).
   ФСЦ в 4 местах (76, 107 — beneficiary; 97, 107 — carrier) отметили «верно» на «совпадает».
   Если пользователь подтвердит, что иностранная ОПФ — это ОПФ, ветка `foreign` должна давать
   «совпадает».
4. Карточка policy: номер ГП в декларации сверяется с пунктом `number` профиля, а профиль
   выбирается по тому же номеру из шапки. Без профиля можно хотя бы проверить, что в поле есть
   номер и дата (как `document`), а сверку оставить на этап 2.
5. Продуктовый конвейер (`app/jobs`) должен передавать карточкам декларацию, прочитанную
   один раз, как `Kept` в eval; иначе время растёт с числом карточек (связано с T-11).

## Вопросы к ФСЦ

1. Иностранная ОПФ (LLC, Co., Ltd и подобные) у выгодоприобретателя и перевозчика —
   «совпадает»? Разметка 76, 97, 107 говорит «да».
2. Если ОПФ в ячейке слита с адресом без пробела или переноса — это «совпадает» или «данные
   неполные»?
3. Для полей document, document_date, document_number, packaging, sealing, other, carrier
   в эталоне нет ни одного «не совпадает»: просим при разметке новых деклараций по шаблону
   отмечать и такие случаи, если они встречаются.
