# Журнал решений

Статусы: **принято** (пользователем), **принято по умолчанию** (действует, пока пользователь не
изменит), **предложено** (ждёт пользователя или заказчика), **отклонено**.

| ID | Решение | Статус |
|---|---|---|
| D-1 | Сетевого каталога нет, все файлы хранятся в системе. Месячная папка «Декларации/{месяц}» из БТ-5 становится полем «месяц» (по дате начала периода страхования) с фильтром; результат скачивается по одному файлу или архивом | принято пользователем |
| D-2 | База знаний «компилируется» в карточки правил по полям (БТ-3a, БТ-4). Бизнес правит базу знаний; система разбирает её на карточки; админ подтверждает; новая версия применяется без перезапуска. Свободный текст базы целиком в промпт не попадает | предложено, на согласовании с заказчиком |
| D-3 | Третий статус «требует проверки» с причиной, в дополнение к «совпадает / не совпадает» | предложено, на согласовании с заказчиком |
| D-4 | Методика НФТ-К — см. [requirements.md](requirements.md) | предложено, на согласовании с заказчиком |
| D-5 | Методика НФТ-В — 30 с при подтверждённом профиле; профиль строится в фоне один раз | предложено, на согласовании с заказчиком |
| D-6 | Приёмка задач — оркестратор; приёмка этапов — пользователь | принято по умолчанию |
| D-7 | Отдельного агента-ревьюера нет: ревью делают `eval` и оркестратор | принято по умолчанию |
| D-8 | Модели по ролям: platform, parser — sonnet; rules, llm, eval — opus | принято по умолчанию |
| D-9 | Субагенты могут читать реальные документы для отладки, но не копировать их в репозиторий | принято по умолчанию |
| D-10 | Обезличивание эталона — скрипт агента `eval`, результат проверяет пользователь | принято по умолчанию |
| D-11 | Полисы и декларации видны всей группе ФСЦ (группа Keycloak); подтверждение профиля и базы знаний — по ролям | принято по умолчанию |
| D-12 | Привязка декларации к полису — автоматически по «№ ГП», с подтверждением в интерфейсе при неоднозначности | принято по умолчанию |
| D-13 | Применение требований к коду к Python — раздел «Требования к коду» в [CLAUDE.md](../CLAUDE.md) | предложено пользователю |
| D-14 | Набор строк результата определяется **формой** декларации (вертикальная — 15 полей, ПСГ — 13), а нумерация «200» или «200/N» — **числом перевозок**. Основание: декл. 35 — ПСГ с одной перевозкой; MVP вывел вертикальные поля, ФСЦ: «поле отсутствует в декл.» | предложено пользователю |
| D-15 | Карточка проверяет всю декларацию сразу (`Card.verdicts(declaration, policy)`), чтобы смысловые вопросы шли одним пакетом и одинаковые значения получали одинаковый результат | предложено пользователю |
| D-16 | Пункт полиса хранится списком редакций с `scope` — «все декларации» или список номеров. ДС к конкретной декларации не применяется к другим (замечания ФСЦ по 76, 97, 107) | предложено пользователю |
| D-17 | Особые условия клиента, меняющие правило поля, хранятся в профиле как пункт `accepted.<поле>` и проверяются движком до основной проверки (декл. 263) | предложено, нужно подтверждение ФСЦ |
| D-18 | Правила ruff RUF001–RUF003 (похожие кириллические буквы) отключены: русский — язык сообщений проекта. FBT003 отключено в тестах: `equal_to(True)` — обычный вызов Hamcrest. Исключения называются с суффиксом Error (требование ruff N818) | принято по умолчанию |
| D-19 | Собственные правила стиля проверяет `python -m tools.lint` (см. [code-style.md](code-style.md)) | принято по умолчанию |
| D-20 | Скиллов `courier:*`, `bugscribe:*` и CLI `gh` в среде нет. До их установки issues создаёт пользователь, коммиты делаются через `git` вручную по правилам CLAUDE.md | предложено пользователю |
