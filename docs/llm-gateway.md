# Шлюз модели и клиент LLM

Документ задачи T-04. Код — `app/llm/`, настройки — `.env.example`, решение пользователя — D-29.

## Клиент

Интерфейс один: `Model.answer(purpose, messages, schema)` возвращает экземпляр pydantic-модели
`schema` или бросает исключение:

- `UnavailableError` — модель не дала ответа: сеть, таймауты, 429/5xx после всех повторов,
  отказ 4xx, пустые ответы после всех повторов, общее время истекло;
- `MalformedError` — ответ дважды не прошёл проверку по схеме;
- `MisconfiguredError` — настройки не позволяют собрать клиент (при запуске).

Вызывающий код на `UnavailableError` и `MalformedError` ставит «требует проверки» с причиной.

Сборка — `Configured(Environment(), journal, ledger).model()`, один объект `Configured` на
процесс: он владеет общим семафором `LLM_MAX_CONCURRENCY`. Семафор потоковый
(`threading.BoundedSemaphore`), клиент синхронный (`httpx.Client`): `Semantics.verdicts`
синхронный, а воркер выполняет синхронный код в потоках.

Слои (снаружи внутрь): `Throttled` (семафор) → `Strict` (снятие рассуждений и обёртки, проверка
pydantic, один повтор, учёт вызовов, общий срок) → `Insistent` (повтор пустого ответа) →
провайдер `Chat` или `Claude` → `Patient` (повтор сети, таймаутов, 429, 5xx) → `Bearer` / `Keyed`
(HTTP).

### Ответ — только JSON

- Схема всегда добавляется в промпт (системное сообщение с JSON-схемой) и, где провайдер умеет,
  ещё и ограничивает ответ: Anthropic — `output_config.format` (structured outputs), Gemini —
  `response_format: json_schema`, шлюз ВСК — по настройке `LLM_RESPONSE_FORMAT`
  (`prompt` по умолчанию, пока разведка не показала поддержку).
- Схема передаётся в строгом виде: все объекты закрыты (`additionalProperties: false`), все поля
  обязательны, ограничения вида `minimum`/`maxLength` убраны (провайдеры их отвергают);
  pydantic всё равно проверяет их после ответа.
- Рассуждения вырезаются: закрытые `<think>…</think>`, текст до одиночного `</think>`
  (так делают шлюзы на vLLM, срезая открывающий тег) и незакрытый `<think>` до конца текста.
- Markdown не разбирается. Снимается только одна обёртка ```` ```json … ``` ````, если она
  охватывает **весь** ответ: модели часто так делают даже при просьбе «без markdown», и
  это не разбор разметки, а снятие конверта; текст с обёрткой внутри остаётся как есть и не
  пройдёт проверку.
- Невалидный ответ — один повтор: модели показывают её ответ и ошибку pydantic с просьбой
  ответить заново. При `temperature=0` простой повтор того же запроса дал бы тот же ответ.
  Второй невалидный ответ → `MalformedError`.

### Повторы

| Что | Сколько | Пауза | Настройки |
|---|---|---|---|
| Сеть, таймаут запроса, 429, 500–599 | до 5 попыток | 5 с | `LLM_RETRY_ATTEMPTS`, `LLM_RETRY_PAUSE` |
| Пустой ответ (`content` null/пусто после снятия рассуждений) | до 3 попыток | 1 с | `LLM_EMPTY_ATTEMPTS`, `LLM_EMPTY_PAUSE` |
| Невалидный JSON | 1 повтор | — | — |
| Прочие 4xx (400, 401, 403, 404, 422) | без повтора | — | — |

Все попытки одного ответа укладываются в `LLM_TOTAL_TIMEOUT` (300 с); один HTTP-запрос — в
`LLM_TIMEOUT` (60 с, как в образце). Ошибки различаются по типу исключения `httpx` и коду
ответа, а не по тексту.

**500 повторяется.** Архитектура требует повторять 5xx; в прошлом MVP шлюз отвечал 500 на
чтении ДС (декл. 7, 29) — если причина в самом запросе (например, слишком длинный документ),
повторы её не исправят, но их ограничивают число попыток и общее время, а итогом будет
исключение, после которого документ помечается непрочитанным, а не падает вся сверка. Если
разведка покажет, что 500 у шлюза всегда детерминирован, повтор 500 стоит убрать.

### Учёт вызовов

Каждый запрос к провайдеру (в том числе повтор после невалидного JSON и неудачный) пишется в
`Ledger`: назначение, провайдер, модель, SHA-256 промпта со схемой, токены на входе и выходе,
задержка, прошёл ли ответ схему. Сейчас есть только `Memory` (в памяти процесса); запись в
таблицу `LLMCall` — пазл в `app/llm/ledger.py`.

### FakeModel

`FakeModel({"назначение": "<JSON>"})` отвечает записанным JSON по назначению запроса, проверяет
его схемой так же, как настоящий клиент, и считает вызовы (`count()`). Сети не касается.

## Провайдеры

Выбор — `LLM_PROVIDER=vsk|anthropic|gemini`. Ключи у каждого провайдера свои: ключ шлюза ВСК
никогда не уходит во внешний сервис, даже если переключить провайдер и забыть сменить ключ.

| | ВСК (`vsk`) | Anthropic (`anthropic`) | Gemini (`gemini`) |
|---|---|---|---|
| Где | контур ВСК | внешний | внешний |
| Адрес | `LLM_API_URL` | `ANTHROPIC_API_URL` (Messages API) | `GEMINI_API_URL` (OpenAI-совместимый) |
| Ключ | `Authorization: Bearer` из `LLM_API_KEY` | `x-api-key` из `ANTHROPIC_API_KEY`, `anthropic-version: 2026-10-21` | `Authorization: Bearer` из `GEMINI_API_KEY` |
| Модель | `LLM_MODEL` | `ANTHROPIC_MODEL` (`claude-sonnet-5-5`) | `GEMINI_MODEL` (заполняет пользователь) |
| JSON | `LLM_RESPONSE_FORMAT` | `output_config.format` | `response_format: json_schema` |
| temperature | 0 | не отправляется (см. ниже) | 0 |
| Рассуждения | `thinking_token_budget` = `LLM_THINKING_BUDGET`, если > 0 | `output_config.effort` = `ANTHROPIC_EFFORT`, если задан | `extra_body.google.thinking_config.thinking_budget` = `LLM_THINKING_BUDGET`, если > 0 |

**Защита данных (правило 10, П-17).** Anthropic и Gemini собираются только при
`LLM_ALLOW_EXTERNAL=true`, иначе `MisconfiguredError` при запуске. При выборе внешнего
провайдера в журнал пишется предупреждение. Через них — только обезличенные или вымышленные
данные; прогон eval на реальных декларациях — только через шлюз ВСК.

**Anthropic без temperature.** Текущие модели Claude (в том числе `claude-sonnet-5-5`) отвечают
400 на любое значение `temperature`, кроме значения по умолчанию, а с версией API `2026-10-21` —
на любое переданное значение. Поэтому `temperature=0` у Anthropic не отправляется; ответ
ограничивается схемой через structured outputs, детерминизм не гарантирован. Бюджет рассуждений
в токенах (`budget_tokens`) у этих моделей тоже убран — вместо него `effort`.

**Gemini через OpenAI-совместимый endpoint.** Тот же протокол chat completions, что у шлюза ВСК:
один код (`Chat`) и одни тесты на оба провайдера; `response_format: json_schema` и
`temperature` поддерживаются. Нативный API потребовал бы третий формат запросов и ответов.
Поле бюджета рассуждений (`extra_body.google.thinking_config`) взято из документации Google
и на реальном API не проверялось.

**TLS.** В образце была отключена проверка сертификата (`verify=False`). Теперь проверка включена
всегда (`LLM_VERIFY_TLS=true`); доверенные — системные сертификаты ОС плюс, если задан,
корпоративный CA из `LLM_CA_BUNDLE` (PEM). Отключение возможно только явной настройкой
`LLM_VERIFY_TLS=false`, с предупреждением в журнале.

## Шлюз ВСК

### Что известно (из класса пользователя)

- `POST {адрес}` — OpenAI-совместимый `/v1/chat/completions`, заголовок
  `Authorization: Bearer <ключ>`.
- Тело: `model`, `messages` (`[{"role": "user", "content": …}]`), `thinking_token_budget`,
  `max_tokens`. Ответ — `choices[0].message.content`.
- `content` приходит `null` или пустым, когда модель израсходовала бюджет на рассуждения —
  такой ответ повторяли до 3 раз с паузой 1 с.
- 503/504, таймауты и ошибки соединения повторяли до 5 раз с паузой 5 с. В прошлом MVP
  шлюз отвечал и 500.
- Ответ содержит рассуждения `<think>…</think>`.
- Таймаут запроса — 60 с.

### Чего не знаем — разведка

| Вопрос | Как проверяет `probe` |
|---|---|
| Поддержка `response_format` (json_object, json_schema) и `guided_json` | раздел 3: запрос в каждом виде, принят ли и проходит ли ответ схему |
| Детерминизм при `temperature=0` | раздел 2: 5 одинаковых запросов, число различных ответов |
| Задержка типичного запроса, токены | раздел 1 |
| Допустимый параллелизм, поведение на 429 | раздел 4: N запросов одновременно без повторов, коды ошибок |
| Поведение `thinking_token_budget` | пустые ответы и `<think>` видны в разделах 1–3; запустить с разными `LLM_THINKING_BUDGET` |
| Модель эмбеддингов в контуре | раздел 5: список моделей `GET …/v1/models` |
| Всегда ли 500 детерминирован | вручную: повторить запрос, на котором шлюз ответил 500 |

### Команда разведки

Запускает пользователь сам, с ключом, в контуре:

```
cp .env.example .env            # заполнить LLM_API_URL, LLM_API_KEY, LLM_MODEL
.venv/Scripts/python -m app.llm probe --parallel 8
```

Параметры: `--parallel N` — сколько запросов отправить одновременно (по умолчанию 8),
`--env путь` — файл настроек (по умолчанию `.env`). Разведка работает с провайдером из
`LLM_PROVIDER`, без повторов (чтобы видеть настоящие коды ответов) и без семафора. Вопрос в
запросах вымышленный, данных клиента нет. Чтобы понять бюджет рассуждений, команду стоит
запустить дважды: с `LLM_THINKING_BUDGET=0` и с рабочим значением из образца.

Пример отчёта:

```
Разведка модели: провайдер vsk, модель …
1. Задержка типичного запроса: 2.31 с, токенов на входе 412, на выходе 37, ответ проходит схему: да
2. Детерминизм: 5 одинаковых запросов, различных ответов 1
3. Ограничение ответа схемой:
   prompt: принято, ответ проходит схему: да, 2.10 с
   json_object: принято, ответ проходит схему: да, 2.05 с
   json_schema: не работает: Модель отклонила запрос с кодом 400: …
   guided_json: принято, ответ проходит схему: да, 2.40 с
4. Параллельность: 8 запросов одновременно, успешно 6, ошибок 2, общее время 5.12 с
   Модель недоступна после всех попыток: шлюз ответил кодом 429: 2
5. Модели (ищите среди них модель эмбеддингов): …
```

Тесты команды ходят только на локальный сервер на порту 0 (`tests/llm/test_probe.py`,
`tests/llm/test_assembly.py`).

### Результаты разведки

Пока нет: ключа у разработчиков нет, команду запускает пользователь. После запуска сюда
вносятся цифры по каждому разделу и выбранные `LLM_RESPONSE_FORMAT`, `LLM_MAX_CONCURRENCY`,
`LLM_THINKING_BUDGET`.
