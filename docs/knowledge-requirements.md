# Требования к базе знаний для сверки деклараций

Для кого: сотрудники ФСЦ, которые готовят базу знаний для сервиса сверки.
Решения, на которых основан документ: D-49, D-53, D-54 ([decisions.md](decisions.md)).

## 1. Зачем сервису база знаний

Сервис сверяет декларацию с ГП и ДС в два приёма:

- **Проверки кодом.** Даты, суммы и лимиты, номера, «поле заполнено», форма организации,
  вхождение в перечень. Они работают по правилам, записанным в сервисе, и база знаний на них
  не влияет. Правила этих проверок согласуются с ФСЦ отдельно, через вопросы к разметке.
- **Смысловые проверки моделью.** Три поля, где нужно понимание смысла: **груз** (относится ли к
  объекту страхования, не входит ли в исключения), **пункт отправления** и **пункт назначения**
  (не на исключённой ли территории). Кроме того, модель извлекает из текста ГП и ДС
  пункты полиса.

База знаний — это инструкции модели для смысловых проверок и для чтения полиса. Модель
получает только те разделы базы, которые относятся к проверяемому полю. Базу целиком она не
видит.

Текущий файл «БЗ Сверка ГП, Сопр. ГП» написан для сотрудника: в нём регламент работы с
заявками, письма, бордеро, счета, акцепты. Модели он не подходит. Нужен отдельный документ по
требованиям ниже.

## 2. Что должно быть в базе

Один раздел на каждое смысловое поле и один — на чтение полиса:

| Раздел | Что описать |
|---|---|
| Груз | Как понимать объект страхования и исключения ГП. Как поступать с общими наименованиями («ТНП», «оборудование», «сборный груз»), со скоропортящимися, опасными, ценными, б/у грузами. Когда нельзя решить по наименованию — нужен человек |
| Пункт отправления | Как сверять с территорией страхования (п. 9 и подобные). Что считать достаточным указанием: город, терминал, условия Инкотермс. Исключённые территории и зоны (JCC, санкционные списки), как с ними поступать |
| Пункт назначения | То же, плюс когда нужен точный адрес и когда хватает города |
| Чтение полиса | Где в ГП и ДС обычно стоят срок, лимиты, территория, объект, исключения, риски. Как ДС меняет пункт ГП. Типичные формулировки, которые легко понять неверно |

Для каждого раздела:

1. **Правило** — 3–10 предложений: что проверяем и с каким пунктом ГП.
2. **Исключения из правила** — когда правило не действует или действует иначе.
3. **Примеры** — не меньше трёх на каждый статус: «совпадает», «не совпадает», «требует
   проверки». В каждом примере: значение из декларации, текст пункта ГП (обезличенный),
   ожидаемый статус и одно предложение «почему».
4. **Когда звать человека** — ситуации, в которых модель должна ответить «требует проверки».

## 3. Чего в базе быть не должно

- Шаги работы сотрудника: Jira, письма, шаблоны ответов, бордеро, счета, акцепты, статусы
  заявок.
- Правила, которые проверяет код: даты, суммы, лимиты, номера, заполненность полей, форма
  организации. Если в них нужно что-то поменять, это вопрос к правилам сервиса, а не к базе.
- Правила, для которых нужны данные вне декларации и полиса: порядковая нумерация
  деклараций, своевременность подачи, «одна ежемесячная декларация за месяц», сверка с
  проформой (D-53).
- Данные клиентов: названия организаций, ИНН, номера полисов, адреса, имена и почта
  сотрудников. В примерах — обезличенные значения («ООО «Ромашка»», «№ 0000T00GR0000»).
- Особые условия отдельных клиентов. Они берутся из файла особых условий ФСЦ и из папки
  полиса (D-50).

## 4. Оформление

- **Формат:** Word (.docx) со стилями заголовков («Заголовок 1» — раздел, «Заголовок 2» —
  подраздел) или Markdown (.md). Без стилей сервис не отличит раздел от обычного абзаца.
- **Названия разделов:** ровно «Груз», «Пункт отправления», «Пункт назначения», «Чтение
  полиса». По названию сервис находит раздел для поля.
- **Объём:** раздел — до 2 страниц (около 2 тыс. токенов), вся база — до 10 страниц. Каждый
  раздел уходит в модель вместе с полисом и сотней значений из декларации; длинный раздел
  вытесняет полезное.
- **Язык:** русский. Термины — как в декларации и ГП. Если в декларациях встречаются
  английские значения, дать английские примеры.
- **Таблицы:** допустимы для примеров, но без объединённых ячеек.

## 5. Изменения базы

- Файл лежит во внешней папке, путь к нему задаётся настройкой сервиса. Менять файл можно без
  выпуска новой версии сервиса.
- В начале файла — версия и дата, в конце — журнал изменений: что поменяли и почему.
- После изменения запускается прогон эталона «до и после» по каждому полю. Если качество по
  какому-то полю упало, изменение откатывается или объясняется. Сервис записывает версию базы
  в каждый результат, поэтому видно, по какой версии сделана сверка.

## 6. Порядок работы

1. ФСЦ готовит раздел «Груз» по этим требованиям.
2. Мы прогоняем эталон с этим разделом и без него и показываем разницу по каждой декларации.
3. По итогам договариваемся о правках и делаем остальные разделы.

Если удобнее, первый вариант разделов можем подготовить мы, из ответов ФСЦ к разметке и
текущих правил сервиса, а ФСЦ его поправит.
