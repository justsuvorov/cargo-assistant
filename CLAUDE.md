# cargo-assistant

Сервис сверки деклараций на перевозку грузов с генеральным полисом (ГП) и дополнительными
соглашениями (ДС). Принцип: **код проверяет, LLM помогает**.

Язык: общение, документация, интерфейс, сообщения об ошибках и логи — на русском;
идентификаторы и docblock'и — на английском.

Главные документы:
- [docs/architecture.md](docs/architecture.md) — устройство приложения;
- [docs/contracts.md](docs/contracts.md) — доменные контракты, ключи полей, карточки, профиль полиса;
- [docs/declarations.md](docs/declarations.md) — как устроены реальные декларации;
- [docs/requirements.md](docs/requirements.md) — требования и трассировка;
- [docs/decisions.md](docs/decisions.md) — журнал решений;
- [docs/plan.md](docs/plan.md) — этапы и задачи;
- [docs/questions.md](docs/questions.md) — открытые вопросы к ФСЦ и пользователю.

## Структура репозитория

```
app/
  domain/       контракты: Protocol + неизменяемые @final-классы. Меняет только оркестратор
  ingest/       файл → нейтральная модель документа (xls/xlsx/doc/docx)
  declarations/ форма, поля, тип, номер, нормализация, RU/EN подписи
  policy/       профиль полиса, редакции на дату, особые условия, перевозчики
  rules/        загрузка карточек, проверки по типам, статусы, причины, комментарии
  semantic/     смысловые проверки (груз, маршрут) через интерфейс Semantics
  llm/          клиент шлюза: JSON-схема, ретраи, лимит параллельности, учёт вызовов
  knowledge/    компиляция базы знаний в карточки
  reports/      запись результата в xlsx, архив
  jobs/         очередь, воркер, стадии и прогресс (граница с фреймворками)
  web/          API и страницы (граница с фреймворками)
  storage/      файловое хранилище
  auth/         Keycloak
  core/         настройки, логирование
cards/          карточки правил (YAML)
tools/lint/     собственный линтер правил Elegant Objects
tools/eval/     прогон эталона и отчёты
tests/          тесты, один файл на модуль; tests/gold/ — эталон (только чтение)
docs/           документы проекта
data/real/      реальные документы клиента (в .gitignore, в git не попадают)
```

Зависимости: `domain` ни от чего не зависит. `declarations`, `rules`, `reports` — без сети и БД.
`rules` не импортирует `llm`: смысловые проверки идут через `app.domain.semantics.Semantics`.
`jobs` и `web` собирают конвейеры, бизнес-логики в них нет.

## Команды

Окружение: `python -m venv .venv` и `.venv/Scripts/python -m pip install -e .[dev]`
(в Linux — `.venv/bin/...`).

Полная проверка перед сдачей задачи (все четыре должны пройти):

```
.venv/Scripts/ruff format --check app tools tests
.venv/Scripts/ruff check app tools tests
.venv/Scripts/mypy
.venv/Scripts/python -m pytest -q
.venv/Scripts/python -m tools.lint
```

## Неприкосновенные правила

Нарушение — основание вернуть задачу.

1. **Код против LLM.** Даты, суммы, лимиты, номера, «поле заполнено», вхождение в список,
   точное и нечёткое совпадение строк проверяет только код. LLM получает только поля с
   `check: semantic` в карточке, извлечение профиля полиса и компиляцию базы знаний.
2. **Ответ LLM — только JSON по схеме**, `temperature=0`. Разбор markdown запрещён. Невалидный
   JSON → один повтор → статус «требует проверки» с причиной.
3. **Три статуса:** совпадает / не совпадает / требует проверки. У каждого результата есть код
   причины, ссылка на пункт ГП/ДС и источник (`rule` | `llm`). Не уверен — «требует проверки».
4. **Бизнес-правила — только в карточках.** В коде нет номеров полисов, имён клиентов,
   конкретных грузов.
5. **Редакция пункта — на дату начала перевозки** (номер ДС + срок действия + к какой
   декларации относится ДС).
6. **Бюджет времени закреплён тестами:** число вызовов LLM на декларацию ограничено константой
   и не растёт с числом строк; разбор декларации < 1 с. Тест считает вызовы через `FakeModel`.
7. **Двуязычие:** у каждой подписи поля есть варианты RU и EN; в фикстурах есть EN-варианты.
8. **Эталон только для чтения.** `tests/gold/` и ожидаемые результаты меняются только с явного
   согласия пользователя. Нельзя «чинить» тест или эталон вместо кода.
9. **Изменение правил, промптов, парсера или профиля** принимается только с отчётом eval
   «до/после» по каждому полю. Регрессия по любому полю → объяснение или откат.
10. **Данные.** В git и фикстуры — только обезличенные данные: без названий клиентов, ИНН,
    номеров полисов, адресов. Реальные документы читаются по путям из `docs/plan.md` или из
    `data/real/`. Ничего не отправляется во внешние сервисы, кроме шлюза модели.
11. **Секреты** — только через переменные окружения / secret, никогда в коде и в git.
12. **Код прошлого MVP не используется.** Каталог `D:\Projects\document-assistant` — только
    источник тестовых данных. Код, ветки и документацию оттуда не открывать и не копировать.
13. **Зависимости между модулями** — по структуре выше. Новая зависимость против направления —
    только через запрос оркестратору.
14. **Требования к коду** (ниже) соблюдаются всегда. Нарушение, которое ловит линтер,
    исправляется, а не подавляется: `# noqa` и `# type: ignore` запрещены.

## Процесс

- Карточку задачи пишет оркестратор. Каждая задача — GitHub issue; ветка называется номером
  issue (например `17`). Не уверен в номере — спроси.
- Перед работой — `git pull`. `git push` и PR — только с явного разрешения пользователя.
- Каждая задача субагента — в отдельном git worktree.
- Сначала тест, потом код. Баг сначала воспроизводится тестом.
- Незавершённое оставляется пазлом: `# @todo #17:30min Что сделать и почему` — единственный
  допустимый вид комментария в коде.
- Запахи кода и рефакторинг вне рамок задачи не исправляются молча, а предлагаются как issue.
- Нужен контракт или файл вне списка → остановиться и вернуть «запрос на изменение».
- Остановиться и спросить, если бизнес-правило неоднозначно, метрика упала или нужны
  реальные данные.

Отчёт субагента (обязательный формат):
1. Что сделано (файлы).
2. Доказательства: команды проверок и их вывод; цифры eval, если задача влияет на качество.
3. Отклонения от карточки.
4. Открытые вопросы.

Без доказательств задача не считается выполненной.

## Требования к коду

Исходный текст заказчика — в [docs/code-style.md](docs/code-style.md). Как он применяется
к Python:

- Каждый класс помечен `@typing.final`, объявляет `__slots__`, хранит от нуля до четырёх
  атрибутов, все атрибуты приватные (`self._x: Final = x`) и задаются только в `__init__`.
- Каждый публичный метод сначала объявлен в `typing.Protocol`. Нет геттеров ради геттеров:
  объект отвечает на вопросы поведением.
- Нет `None` в аргументах и результатах (кроме `-> None` у команд). Пустое значение —
  отдельный объект (`Blank`, `Absent`).
- Нет `@staticmethod`, `@classmethod`, утилитных классов и имён на -er (`Cards`, а не
  `CardLoader`).
- Нет `isinstance`, `type()`, `getattr`, `cast` в коде приложения: различия — через полиморфизм.
- Нет комментариев в коде, кроме пазлов PDD; docblock у каждого класса объясняет назначение.
- В телах методов нет пустых строк. Одноразовые выражения встраиваются.
- Методы называются одним существительным или глаголом; команды отделены от запросов.
- Сообщения об ошибках и логи — одно предложение с контекстом, без точки в конце.
- Ошибка — сразу и громко; молча проглатывать нельзя.

Границы с фреймворками (ORM SQLAlchemy, роуты FastAPI, pydantic-схемы, миграции Alembic)
живут только в `app/jobs/`, `app/web/`, `migrations/` и в подпапках `schema/` модулей. Там
правила Elegant Objects применяются не буквально. Через границу в домен передаются только
доменные объекты.

Тесты:
- `pytest` + `PyHamcrest`; один `assert_that(..., ..., "сообщение")` последней строкой;
- сообщение сформулировано через отрицание («... does not ...»), без апострофов;
- имя теста — предложение (`test_rejects_date_after_policy_end`);
- один тестовый файл на один модуль: `tests/<путь>/test_<модуль>.py`;
- без общих фикстур, `setUp`, констант; файлы — в `tmp_path`; данные — случайные там, где
  значение не важно;
- без сети: модель только `FakeModel`, сервер на порту 0; логирование в тестах выключено;
- каждое ожидание ограничено таймаутом.
